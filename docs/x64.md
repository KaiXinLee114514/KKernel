# x86-64 start64 (Phase 1 MVP)

> The 32-bit kernel can now hand over to a **real 64-bit kernel**: type `start64` in the shell,
> the kernel loads `BIN/K64.BIN` from the FAT disk, builds page tables, sets `EFER.LME`,
> jumps into long mode, and the independent 64-bit kernel takes over with its own GDT / IDT /
> PIC / PIT / keyboard driver / LFB console / shell.
>
> It is **one-way** on purpose: Phase 1 does not implement `start32`, so there is no way back
> except `reboot`. The point of this phase is a clean, self-contained 64-bit boot path and a
> shell that proves long mode, interrupts, the keyboard and the framebuffer all work.

## What works

- 32-bit side: `start64` command (in `kernel/x64.asm`)
  - CPUID check: PAE (CPUID leaf 1, EDX bit 6) + long mode (leaf `0x80000001`, EDX bit 29);
    a friendly error is printed on a CPU without long mode.
  - loads `BIN/K64.BIN` through the normal FAT driver into physical `0x200000` (max 128 KiB);
  - fills a `K64I` boot-info block at `0x1FF000`;
  - builds identity page tables (2 MiB pages): `0x00000000-0x3FFFFFFF` plus the VBE LFB window
    `0xC0000000-0xFFFFFFFF`;
  - switches to long mode and far-jumps to `0x200000`.
- 64-bit side (`kernel64/`, flat binary linked at `0x200000`, assembled with `nasm -f bin`):
  - own GDT and a 256-entry IDT; 32 CPU exception stubs that print vector / error code /
    RIP / CS and halt instead of triple-faulting;
  - PIC remapped to `0x20`/`0x28`, PIT at 100 Hz, PS/2 keyboard with set-1 scancode
    translation (letters, digits, shift, space, enter, backspace);
  - direct VBE 32bpp LFB console (800×600 by default) with the same 8×16 ASCII font as the
    32-bit console, scrolling and a green/white palette;
  - shell with `help`, `info`, `echo`, `clear`, `ticks`, `reboot`;
  - `info` reports the CPU vendor, CR0/CR4/EFER, `PAE=1 LME=1`, memory, LFB and the K64 image
    location.
- Tests: `make -s test-k64` logs in on the 32-bit shell, runs `start64`, and checks the banner,
  `k64>`, `info` (`PAE=1`, `LME=1`), `echo hello64`, `ticks` and finally `reboot` (QEMU exits
  because of `-no-reboot`).

## Usage

In the 32-bit shell (HD image, after logging in as `root`/`root`):

```text
(・ω・)> start64
start64: jumping to 64-bit kernel at 0x03010000 (long mode)
KKernel x86-64
long mode: enabled
  LFB: 0xFD000000 800x600x32
  RAM: 127 MiB, E820 entries: 7
  K64: 0x03010000, 11040 bytes
k64> info
...
k64> reboot
```

> ⚠️ **QEMU note**: `qemu-system-i386` cannot emulate long mode — all its CPU models have the
> CPUID long-mode bit filtered out, so `start64` correctly reports "CPU does not support long
> mode (PAE/LM)". The `--k64` test and manual runs must use `qemu-system-x86_64` (with
> `-cpu qemu64` or better). This is a property of the i386 emulator target, not of the kernel.
>
> ⚠️ **RAM note**: `start64` needs **at least 64 MiB** of physical RAM. The page tables,
> boot-info block, the 64-bit stack and the `K64.BIN` image all live in the `0x03000000`
> (48 MiB) region. On smaller machines the command prints
> `start64: need more RAM (at least 64 MiB)` and stays in the 32-bit shell.

## Boot information block (`0x0300F000`)

| Offset | Size | Meaning |
|---|---|---|
| 0 | 4 | magic `K64I` (`0x4934364B`) |
| 4 | 4 | LFB physical address |
| 8 | 4 | LFB pitch (bytes per scanline) |
| 12 | 4 | LFB width in pixels |
| 16 | 4 | LFB height in pixels |
| 20 | 4 | LFB bits per pixel |
| 24 | 4 | E820 entry array pointer (`0x9400`) |
| 28 | 4 | E820 entry count |
| 32 | 4 | RAM top (MiB) |
| 36 | 4 | K64 image physical address (`0x03010000`) |
| 40 | 4 | K64 image size in bytes |
| 48 | 8 | 64-bit stack top (`0x0300D000`) |

## 32-bit → 64-bit memory layout

| Physical address | Use |
|---|---|
| `0x00100000+` | 32-bit kernel, FAT buffer, program windows, pmem pool (unchanged) |
| `0x03000000` | PML4 (one entry) |
| `0x03001000` | PDPT (identity for 0–1 GiB, LFB window for 3–4 GiB) |
| `0x03002000` | PD0: 512 × 2 MiB pages covering `0x00000000-0x3FFFFFFF` |
| `0x03003000` | PD3: 512 × 2 MiB pages covering `0xC0000000-0xFFFFFFFF` (LFB at `0xFD000000`) |
| `0x03004000`–`0x0300D000` | 64-bit kernel stack (grows down from the top) |
| `0x0300D000` | 64-bit kernel stack top |
| `0x0300F000` | boot information (`K64I`) |
| `0x03010000` | `BIN/K64.BIN` load address / 64-bit kernel `ORG` |

Why `0x03000000`? Never place these structures inside the 32-bit kernel's own heap
(`0x180000-0x6E0000`) or the page pool (from `0x400000`). The original Phase-1 addresses
(`0x1E0000`-`0x200000`) sat inside the kernel heap: QEMU happened to survive it, but
VirtualBox triple-faulted (`GURU_MEDITATION`) right after the page tables were switched and
the new `LGDT` executed. Moving the whole block to `0x03000000` (48 MiB) fixes that; it also
means `start64` needs 64 MiB of RAM. The 256 KiB block `0x03000000-0x03040000` is additionally
marked used via `pmem_reserve()` right after `pmem_init` (see `kernel/pmem.asm`), so page-pool
allocations can never hand out these pages; on machines whose pool ends below 48 MiB the
reservation is a safe no-op.

The `#GP`-on-`retf` lesson: when `EFER.LMA=1` (in compatibility mode) QEMU reads the `LGDT`
operand as a full 10-byte descriptor, and a data segment descriptor must not carry `L=1`
until the CPU is really executing 64-bit code — the transition GDT therefore uses a normal
32-bit-compatible data descriptor and the 64-bit kernel reloads its own GDT after the far jump.

## Build, run, test

```bash
make k64                                   # build/K64.BIN (64-bit flat binary)
make -s -B build/kkernel-hd.img            # packs BIN/K64.BIN into the FAT image
make -s test-k64                           # automated QEMU test (x86_64 emulator)
# manual:
qemu-system-x86_64 -m 128 -cpu qemu64 -boot c \
  -drive file=build/kkernel-hd.img,format=raw,if=ide,index=0 \
  -display none -no-reboot -monitor unix:/tmp/kk.mon,server,nowait
```

Sizes (Phase 1): 32-bit `kernel.bin` ≈ 155 KiB (limit 256 KiB); `K64.BIN` ≈ 11 KiB
(limit 128 KiB, must fit in a single FAT read).

## Files

| File | Purpose |
|---|---|
| `kernel/x64.asm` | 32-bit side: `start64` command, CPUID checks, page tables, long-mode switch |
| `kernel64/start.asm` | 64-bit entry point, own GDT, boot-info validation, init sequence |
| `kernel64/console.asm` | direct LFB 32bpp text console (8×16 ASCII font, scrolling) |
| `kernel64/idt.asm` | 64-bit IDT, exception stubs, PIC remap, PIT and keyboard IRQ handling |
| `kernel64/shell.asm` | 64-bit shell: `help / info / echo / clear / ticks / reboot` |
| `tools/mkfont8x16.py` | extracts the ASCII 8×16 glyphs from `font/font-kkf.bin` |
| `build/font8x16.bin` | generated ASCII font blob, `incbin`-ed by `kernel64/start.asm` |
| `tests/qemu_test.py --k64` | automated test (uses `/usr/bin/qemu-system-x86_64`) |

## Known limitations (Phase 1)

- One-way: no `start32`, no way back to the 32-bit kernel; `reboot` restarts the whole machine.
- The 64-bit kernel is a single-threaded ring-0 program: no user mode, no processes, no
  scheduler, no page allocator, no swap.
- Only the hardware it needs: PIC (8259A), PIT (channel 0, 100 Hz), PS/2 keyboard controller,
  VBE linear framebuffer. No disk driver, no USB, no network, no IME.
- Keyboard is US QWERTY only (set-1 scancodes); no numpad/arrows/extended keys beyond basic
  shift handling.
- 32-bit kernel must stay under 256 KiB and `K64.BIN` under 128 KiB (single FAT read limit).
