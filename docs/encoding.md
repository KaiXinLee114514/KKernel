# The State of Text Encoding in KKernel

This document answers one question: **what encoding does text in KKernel actually use, and is it standard?**

The one-line answer: **the character numbers are standard Unicode code points, and the kernel's text is now standard UTF-8** — a string can be `db`'d straight into the kernel, and it matches the files on disk, your editor, and git. Nobody has to learn a second encoding.

> History: for a while the kernel stored Chinese as an array of "one u32 per code point" (fast to look up, but out of step with everything outside). Sections 2.2 and 2.3 keep a record of that representation and its pitfalls; Section 6 covers the switch to UTF-8 and what was measured afterwards.

Below I take each stage apart and mark which parts are standard and which are our own invention.

## 1. At a Glance

| Stage | What it uses | Standard? |
|---|---|---|
| Font source data `font/unifont-subset.hex` | GNU Unifont's `.hex` format (`codepoint:bitmap`) | ✅ Standard (anyone can pick it up and use it) |
| Font binary `font/font-kkf.bin` | Custom container KKF0; **key = Unicode code point** | ⚠️ Custom container, standard keys |
| English/ASCII strings in the kernel | Plain 0-terminated byte strings | ✅ Valid UTF-8 (ASCII is a subset of it) |
| Chinese text in the kernel | **UTF-8 byte strings** (`db 'KKERNEL 上线，欢迎回来。', 0`) | ✅ Standard |
| Terminal print interface | `term_print` decodes UTF-8 into code points, then everything goes through `term_print_cp` | ✅ One path for Chinese and English |
| Text mode's "two cells from font slot 0x80" | VGA font slot index | ❌ **This is not an encoding**, it's a hardware slot hack |
| Keyboard input | PS/2 scancode → ASCII character events | Plus a separate **Shift pinyin IME** (see 2.4), which composes UTF-8 before it reaches the command line |

## 2. Taking Each Stage in Turn

### 2.1 Font: the keys are standard code points

`tools/unifont2bin.py` converts Unifont's `.hex` into the KKF0 format the kernel can `incbin` directly:

```
+0  'J''O''Y''F'   +4 version   +8 glyph count   +12 data offset
each entry is 12 bytes: code point (u32), width (1), height (1), reserved (2), data offset (4), ascending by code point
data: 8 wide is 1 byte per row, 16 wide is 2 bytes per row, most significant bit leftmost
```

A quick lookup shows the keys really are Unicode code points:

```
query 'A'  → U+0041  width 8   height 16
query '你' → U+4F60  width 16  height 16
query '好' → U+597D  width 16  height 16
```

**The container format (KKF0) is our own invention**, not a standard bitmap font format (BDF / PCF / PSF / Unifont `.hex` are the standard ones). It exists purely so that table lookup inside the kernel is simple: fixed-size entries + sorted by code point → binary search, no text format to parse. The source data is still standard `.hex`, so the data itself never got "privatised".

### 2.2 Chinese in the kernel: a code point array, not UTF-8

> ⚠️ **This section records the state before the conversion** (kept for history and as a pitfall record); the conversion was completed in Section 6.

Chinese text was generated by `tools/unifont2bin.py` as a **code point array** (`font/vga-zh-strings.asm`):

```asm
zh_str_1:
    dd 0x00004F60, 0x0000597D, 0x0000FF0C, 0x00004E16, 0x0000754C, 0x0000FF01, 0
    ;  你          好          ，          世          界          ！        end
```

What that representation is:

* every character is a fixed 4 bytes, code point stored little-endian → effectively **UTF-32LE in memory**
* no BOM, terminated by a 0 dword (not length-prefixed)
* therefore it is **not** any standard "text byte stream" format: UTF-32 as a file/interchange format normally carries a BOM, and ours is an in-memory array with a 0 terminator — closer to an "internal representation" than to an "encoding"

Printing went through `term_print_zh` (esi = array start) → calling `term_print_cp` per item (eax = code point) → graphics mode enters `fb_putcp` to look the glyph up and blit it, text mode looks up the font slot table.

### 2.3 The terminal didn't eat UTF-8 (with evidence)

> ⚠️ **This section records the state before the conversion** (kept for history and as a pitfall record); the conversion was completed in Section 6.

`term_print` was `lodsb` — one **byte** at a time — followed by `term_putc`:

* text mode: the byte was written straight into `0xB8000` as a character code → UTF-8 Chinese therefore showed up as accented Latin letters (that's where the "mojibake" in those early screenshots came from)
* graphics mode: the byte was treated as a code point and looked up in the font → a miss drew the **missing-glyph box □** (`missing_glyph` in `fbterm.asm`)

So stuffing UTF-8 Chinese into `term_print` produced **a row of boxes** — it actually happened during development, and it's a handy tell for "this didn't take the UTF-8 path".

### 2.4 Keyboard: ASCII scancodes + a pinyin IME

`kernel/keyboard.asm` maps scancodes through a table into characters: ASCII (0x20-0x7E) plus Enter/Backspace/Tab, and a lone **Shift** press emits a `KBD_IME_TOGGLE` (0x1F) event.

Chinese input is supplied by the **pinyin IME** (rendered in the candidate bar in the shell / editor):

* the word list lives on disk as `/SYS/PINYIN.BIN` (generated by `tools/mkpinyin.py`): a `PIME` header + syllable table + entries sorted by word frequency
* in Chinese mode a-z first accumulate into a pinyin syllable; Space / Enter looks it up → candidates pop up on the bottom two rows of the screen (candidates on the first row, pinyin echo on the second)
* digits 1-9 / Space pick, `,` / `.` page, Esc cancels; the picked character is a **standard three-byte UTF-8 sequence** that goes straight into the shell line buffer / editor body — the same encoding path as the contents of a file shown by `cat`
* so "the keyboard only emits ASCII" describes the **hardware scancode path**; the text that finally reaches a program is already UTF-8

### 2.5 That "two cells of font slot numbers" thing is not an encoding

In the text-mode experimental path, a Chinese character was split into left and right halves and placed in two VGA font-table slots starting at 0x80, and printing wrote the two bytes back to back. **Those two bytes are hardware font slot numbers, not character numbers** — swap in a different font table for the same character and the slot numbers change. It is only used by the text-mode experiment (`make run-font`); the real path (graphics mode) looks glyphs up by code point.

## 3. Why It Was Chosen That Way Back Then

* at first I only needed to show **a few fixed Chinese strings**; a code point array is the fastest thing to look up and there was no decoder to write
* the lookup interface is naturally "code point"-shaped, so the font side was standard from day one
* the price was that **interchanging text with the outside world** got blocked (UTF-8 files on disk, git, editors — none of them spoke our format)

That was a trade-off, not an oversight: the goal at the time was "get Chinese onto the screen", not "build a system that can read files".

## 4. How to Standardise It (**this section has been carried out**, see Section 6)

Turn it into a **UTF-8 decoder** and fill in the "byte stream → code point" step. **Not a single glyph in the font or code point table has to change.**

1. **`kernel/utf8.asm`** (new, about 30-40 lines)
   * `utf8_decode`: esi points at the byte stream, out eax = code point, esi advances 1-4 bytes
   * 1 byte `0xxxxxxx`, 2 bytes `110xxxxx 10xxxxxx`, 3 bytes, 4 bytes
   * invalid sequences (truncated, illegal lead byte, out of range, overlong encoding, surrogate range) → return U+FFFD (`�`)
2. **Rework `term_print`**: loop `utf8_decode` → `term_print_cp`, one path for Chinese and English
   * text mode keeps using the font slot table (it already looks up by code point anyway)
   * so both display modes support UTF-8 automatically
3. **Change the string generation**: add an "emit a UTF-8 byte string" mode to `tools/unifont2bin.py`, and `font/strings.txt` gets `db`'d into the kernel as-is (`db 'KKERNEL 上线，欢迎回来。', 0`) instead of being a `dd` code point array
4. **Regression check**: the existing **pixel-by-pixel template match** on those 6 lines of Chinese doubles as the regression test — after changing the encoding, the screen should look **exactly the same**, without editing a single assertion
5. Tests you get for free along the way:
   * a 4-byte sequence (e.g. U+1F600 😀): needs the corresponding glyph added to the font subset too (Unifont has it)
   * a deliberately truncated byte sequence → expect it to draw `�`

Once that's done, "font indexed by code point" + "kernel text is UTF-8" are both standard, and hooking FAT12 up to read UTF-8 files, writing a `cat`/`echo`, all follow naturally.

## 5. One-Line Cheat Sheet (current state)

* **Code points**: standard Unicode all along ✅
* **Font source** `.hex`: standard ✅; container KKF0: custom, but the keys are standard ⚠️
* **Chinese text in the kernel**: **standard UTF-8** ✅ (`db 'KKERNEL 上线，欢迎回来。', 0`, see Section 6; the pre-conversion "code point array" stays in 2.2 as history)
* **Text files on disk**: standard UTF-8 ✅ (`cat` prints them directly, `write` stores them as-is)
* **Font slot numbers** (the text-mode experimental path): not an encoding ❌

## 6. Done: Kernel Text Is Uniformly UTF-8

The plan from Section 4 above has landed (`kernel/utf8.asm` + the `term_print` rework + string generation switched to `db`); the current state:

```asm
zh_str_1:
    db 'KKERNEL 上线，欢迎回来。', 0        ; ← a plain standard UTF-8 byte string, straight from font/strings.txt
```

* **`kernel/utf8.asm`**: `utf8_decode` (esi = byte stream → eax = code point, esi advances automatically)
  * decodes 1/2/3/4-byte sequences; ASCII is just a special case of it
  * three validity checks: illegal lead byte / truncated sequence / overlong encoding / surrogate range (D800-DFFF)
  * a bad byte returns **U+FFFD (the replacement character `�`) and advances only one byte** — if a chunk in the middle of the data is rotten, the text after it still shows up and nothing gets stuck (measured: a truncated 3-byte sequence plus one stray continuation byte → two `�` on screen, and the English after them keeps printing)
* **`term_print`**: loops `utf8_decode` → `term_print_cp`, so
  * graphics mode: `fb_putcp` looks the glyph up by code point → blit
  * text mode: looks up the font slot table by code point → writes `0xB8000`
  * **both modes support UTF-8 automatically**, one path for Chinese and English, and control characters (`\n \r \b`) are branched off inside `term_print_cp`
* **4 bytes verified as well**: 😀 (U+1F600) is 16×16 in the font and really does render
* **Regression tests**: the original **pixel-by-pixel template match on those 6 lines of Chinese passes with not one change** — after an encoding change the pixels on screen should be identical, and that is the best regression evidence there is; three assertions were added: UTF-8 three-byte (Chinese), four-byte (emoji), bad byte (replacement character)

Not done yet (doesn't affect "the encoding is standard"):

* the keyboard scancode path still emits ASCII only (but the pinyin IME above has since covered Chinese input)
* text files on disk can now be read: the shell's `cat <file>` hands the UTF-8 buffer read from FAT16 straight to `term_print` (see [filesystem.md](filesystem.md)) — that's how the Chinese in `progs/README.TXT` gets displayed
